# Хакатоны, кейсы и критерии

## Жизненный цикл

1. Организатор создаёт черновик с будущим началом и дедлайном.
2. Добавляет кейсы и критерии каждого кейса.
3. Публикует хакатон. Публикация требует минимум один кейс и минимум один критерий
   у каждого кейса. Пустой или незавершённый хакатон не публикуется.
4. До старта можно снять хакатон с публикации, изменить черновик и опубликовать снова.
5. Начиная со старта сроки, кейсы, критерии и публикация неизменяемы.

Сервер проверяет permission и `organizer_id`. Другой организатор или администратор
не может просматривать черновики и управлять чужими мероприятиями.
`organizer_id` задаётся из текущей сессии, поле нельзя передать в запросе.
Все изменения кейсов, критериев и публикации блокируют строку хакатона до commit:
параллельные операции не могут опубликовать конфигурацию между её изменениями.

## Время и видимость

Все даты требуют часовой пояс в ISO 8601, например `2031-01-02T05:00:00+05:00`.
Они нормализуются в UTC и хранятся как PostgreSQL `timestamptz`.
Дата без часового пояса отклоняется. Дедлайн должен быть строго позже начала.
`GET /api/v1/time` возвращает серверное время, независимое от часов клиента.

| Состояние | Публичное описание хакатона | Материалы и критерии кейсов |
|---|---|---|
| Черновик | 404 | 404 |
| Опубликован, до начала | Видно | 403 |
| `starts_at <= server_time < deadline_at` | Видно | Доступны |
| В момент дедлайна и после него | Видно | 403 |

`description` самого хакатона — публичный анонс; закрытые задания помещаются
в `description` кейсов. Публичные списки не включают кейсы и критерии.
Организатор читает свои материалы в любое время через `/organizer/...`.
Назначенный эксперт после дедлайна получает решение и критерии через маршруты
оценивания. Сдача и её серверный дедлайн описаны в [SUBMISSIONS.md](SUBMISSIONS.md).

## API

Все пути ниже начинаются с `/api/v1`.

| Метод и путь | Назначение |
|---|---|
| GET `/time` | Серверное время UTC |
| GET `/hackathons?limit=20&offset=0` | Опубликованные хакатоны, по ID |
| GET `/hackathons/{id}` | Анонс, server_time, phase, materials_available |
| GET `/hackathons/{id}/cases` | Кейсы с критериями в разрешённый период |
| GET `/organizer/hackathons` | Только свои мероприятия, включая черновики |
| POST `/organizer/hackathons` | Создать черновик |
| GET, PUT `/organizer/hackathons/{id}` | Прочитать / полностью изменить свой черновик |
| POST `/organizer/hackathons/{id}/publish` | Опубликовать |
| POST `/organizer/hackathons/{id}/unpublish` | Снять с публикации до старта |
| GET, POST `/organizer/hackathons/{id}/cases` | Прочитать / создать кейс |
| PUT, DELETE `/organizer/hackathons/{id}/cases/{case_id}` | Изменить / удалить кейс черновика |
| PUT `/organizer/hackathons/{id}/cases/{case_id}/criteria` | Атомарно заменить критерии кейса |

Лимит списков хакатонов: 1–100, по умолчанию 20. Методы PUT требуют полный объект.
При замене критериев старые ID заменяются новыми; после старта замена запрещена.
Вложенный case_id всегда проверяется на принадлежность указанному хакатону.

## Пример для Swagger

Войти как `demo-organizer`, вставить access_token в Authorize.
Создать хакатон с будущими датами:

```json
{
  "title": "Учебный хакатон",
  "description": "Создание полезных веб-сервисов",
  "starts_at": "2031-01-02T00:00:00Z",
  "deadline_at": "2031-01-04T00:00:00Z"
}
```

Создать кейс:

```json
{"title": "Сервис команд", "description": "Разработать API управления командами"}
```

Установить критерии через PUT:

```json
{
  "criteria": [
    {"title": "Функциональность", "min_score": 0, "max_score": 10, "weight": "3"},
    {"title": "Качество кода", "min_score": 0, "max_score": 5, "weight": "1"}
  ]
}
```

Опубликовать. До старта публичное описание доступно, публичные кейсы дают 403,
а организатор видит их через собственный маршрут. Для живой демонстрации периода
выберите близкое будущее начало; тесты проверяют границы с управляемым серверным временем.

## Договорённость о расчёте рейтинга

Баллы целочисленные: `0 <= min_score < max_score <= 1000`. Вес — положительное
десятичное число до 1000, максимум четыре знака после запятой. Сумма весов
не обязана быть 1 или 100. У кейса от 1 до 30 критериев.

Итог одной полной экспертной оценки рассчитывается так:

```text
normalized_i = (score_i - min_score_i) / (max_score_i - min_score_i)
expert_total = 100 * sum(weight_i * normalized_i) / sum(weight_i)
final_total = mean(expert_total по завершённым валидным оценкам экспертов)
```

Промежуточные вычисления — Decimal без округления; итог округляется до двух знаков
с ROUND_HALF_UP. Например, при весах 3 и 1, баллах 8/10 и 5/5 итог — 85.00.
Неполные оценки не участвуют; отсутствие полных оценок означает «не оценено»,
а не нулевой балл. Сравнивать проекты следует в пределах одного кейса с одинаковыми
критериями. API и правила рейтинга описаны в [SCORING.md](SCORING.md).
